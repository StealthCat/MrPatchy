# Development instructions

- Read CONTRIBUTING.md, docs/SECURITY_IMPLEMENTATION.md and docs/DEVELOPMENT_COORDINATOR.md. Before roadmap work or a no-op decision, list all open GitHub issues and inspect candidate reports/comments and related PRs. Reproduce feasible issues against current main before fixing; reconcile unfinished fixes first.
- Reproducible issue fixes take priority over roadmap work, including when the feature roadmap is complete. Link fully resolved issues with Fixes/Closes in the PR. Leave blocked/unreproducible reports open and report access failures honestly.
- Apply the read-only completion gate after triage. Stop without speculative edits, commits or version bumps only when neither actionable issue fixes nor unfinished requested roadmap work remains.
- Work in a focused feature branch targeting main. Preserve the mascot/theme, roles, audit history and explicit response authorization boundaries. Development coordination never authorizes runtime response actions.

## Parallel implementation workers

User instruction (2026-10-31): independent development may run concurrently; one integration coordinator owns versioning, merging and issue closure. This replaces the former requirement that every worker version and merge its own update.

- Start with at most **two active implementation streams** across the repository. A stream is an issue-owned branch receiving implementation edits; ready PRs waiting for integration and read-only review do not consume a slot. Do not create extra streams merely because more scheduled runs start. Reconcile existing work rather than abandoning it to meet the limit. Increase the limit only on explicit user instruction.
- At the start of each run, refresh current main, open issues, issue comments, open PRs and relevant PR reviews/checks. Reconcile unfinished work, active ownership and available capacity before selecting a task. A scheduled cycle ending does not imply abandonment.
- Before implementation, claim an existing issue in a comment, or create a scoped issue for an explicitly requested task that has none. Include an agent/session identifier, UTC timestamp, outcome, affected areas, branch/PR and next checkpoint. Shared account names, assignees and labels alone do not identify a worker.
- Re-read the issue and related PRs immediately after claiming and before substantial edits. A comment is not an atomic lock. Resolve overlapping claims by division or handoff before editing. If ownership/capacity is unclear, review existing work or report the blocker instead of duplicating a fix.
- Use a separate focused branch and isolated checkout for every stream. Open a linked draft PR as soon as work is reviewable and update that same PR on later runs. Never reset another worker's checkout, overwrite its changes, force-push its branch or take over its PR without a handoff.
- Coordinate dependencies and shared-file changes explicitly, especially database migrations, authentication, scheduling and response authorization. Independent file edits can still conflict in behavior. Split dependent work or agree a sequence before implementation.
- Workers **do not allocate/bump APP_VERSION, edit README.md or CHANGELOG.md, add version prefixes/labels, merge/close PRs, enable auto-merge or close implementation issues**. Keep change notes, compatibility impacts, reproduction evidence and validation in the PR description and issue checkpoints. All README/changelog notes and updates belong to the coordinator; workers put proposed documentation text in the PR body.
- Development commits and PR titles use descriptive subjects without a required version prefix. Preserve existing commits, including legacy versioned subjects; do not rewrite history just to remove prefixes.
- Run relevant checks, including `python tools/check_version.py --base-ref <current-main-commit> --allow-unversioned`. The separate CI `integration-version` gate is expected to fail until coordinator preparation; other applicable checks must pass before a ready handoff.
- Post concise checkpoints when scope changes, a run ends, work blocks or a handoff is needed: exact commit/PR, completed work, validation, remaining work and ownership. Retain an unfinished claim across runs; release it explicitly when stopping work permanently.
- When complete, mark the PR ready for review and record **Ready for coordinator: <exact head SHA>**, acceptance criteria, checks, dependencies and integration permission. This grants the designated coordinator permission to append integration/version/conflict-resolution commits to that branch without discarding implementation. Stop worker edits after handoff; withdraw readiness and notify the coordinator before making further changes.
- Workers may review each other's PRs. Identify the reviewing session and exact reviewed commit; never present self-review through a shared account as independent approval. If all actionable work is owned or capacity is full, report that state; do not invent changes or declare the roadmap complete.

## Single integration coordinator

- Only one designated coordinator session may integrate at a time. Use a persistent GitHub coordination issue to record session ownership, UTC checkpoints, active PR/head/base and handoffs. Resume the same coordinator's work or obtain an explicit handoff; do not assume an old-looking comment is an expired lock. Comments are coordination records, not atomic locks or access controls. Do not run overlapping coordinator sessions.
- Refresh main, open issues/PRs, comments, reviews, CI and dependency state. Prioritize reproducible defects and unblock existing work. Integrate **one PR at a time** in dependency/risk order; do not start a second integration while the first is awaiting checks or merge.
- Require a ready handoff before writing another worker's branch. Review scope, acceptance criteria and code independently of the worker's report. Return substantive missing work to its owner; preserve all unrelated merged changes. Existing versioned PRs require the same handoff and may be adopted without rewriting their commits.
- Merge current main into the handed-off branch using a normal integration commit; resolve metadata conflicts and only well-understood code conflicts. Return ambiguous behavioral conflicts to the owner. Choose a final version from current main at integration time, not by reserving versions across worker PRs.
- For every completed PR integration, increment APP_VERSION in app/main.py using **1.MINOR.PATCH**: patch for incremental code/UI/installation/documentation changes, minor for substantial compatible features. Major stays **1** until explicitly changed by the user (2026-10-30). Never reuse/decrease a merged release version or rewrite past commits; document breaking compatibility impacts while retaining major 1.
- Handle all README.md and CHANGELOG.md notes and updates from the worker's PR description, checking them against the delivered implementation. Update README features/installation/usage where needed without a current-version field. Prepend one versioned, numbered CHANGELOG.md entry describing this PR's delivered changes, compatibility impacts and a canonical `[PR #N](https://github.com/StealthCat/MrPatchy/pull/N)` link. Preserve existing main changelog history verbatim. The changelog records delivery through each PR merge; workers keep unmerged notes in their PRs rather than a shared Unreleased section.
- README has no current-version field and is excluded from version synchronization. UI, health, identity and FastAPI metadata continue deriving their version from APP_VERSION.
- The coordinator's integration/version commit, final PR title and merge/squash commit subject include `[vX.Y.Z]`. Add the matching version label where supported; label creation failure does not block valid work. Legacy worker version prefixes are not reservations. Git tags remain skipped by user instruction; a source bump does not publish a Docker image.
- Run `python tools/check_version.py --base-ref <current-main-commit> --pr-number <PR-number>` and all applicable checks on the exact final integration commit. The CI `integration-version` gate must pass, along with every other applicable check. Development-mode success alone never authorizes a merge.
- Immediately before merge, re-read main, PR head, readiness, reviews and checks. Confirm the tested head is unchanged and incorporates current main; use an expected-head SHA when merging. If main advances or any commit changes, integrate again, reassess the version and rerun affected checks on the new final commit. Never bypass a failed/pending check to meet a schedule.
- After a successful merge, verify the merge commit/version/changelog and that fully resolved linked issues closed. Retain partially delivered or blocked issues. Close unmerged duplicates/superseded PRs only with documented evidence and links; never close unfinished work merely to clear the queue. Record merge/check/issue links and release or checkpoint coordinator ownership.
- If no PR is ready, report blockers without speculative code, empty version bumps or invented work. If GitHub cannot be read or updated, report the access blocker rather than assuming ownership or success.

The copyable coordinator prompt and transition procedure are in docs/DEVELOPMENT_COORDINATOR.md. Existing schedules and the issue-first completion gate remain unchanged.
