# Development instructions

- Read CONTRIBUTING.md and docs/SECURITY_IMPLEMENTATION.md. Before roadmap work or a no-op decision, list all open GitHub issues and inspect candidate reports/comments and related PRs. Reproduce feasible issues against current main before fixing; reconcile unfinished fixes first.
- Reproducible issue fixes take priority over roadmap work, including when the feature roadmap is complete. Link fully resolved issues with Fixes/Closes in the PR and verify closure after a tested merge. Leave blocked/unreproducible reports open and report access failures honestly.
- Apply the read-only completion gate after triage; no changes or version bumps only when neither actionable issue fixes nor unfinished requested roadmap work remains.
- Work in a focused feature branch targeting main. Reconcile unfinished related PRs first. Preserve the mascot/theme, roles, audit history and explicit response authorization boundaries.
- For every completed update, increment APP_VERSION in app/main.py using the MAJOR.MINOR.PATCH format (patch for incremental changes, minor for substantial compatible features). Never reuse/decrease versions or rewrite past commits.
- Major version is fixed at 1 until an explicit user instruction changes it (user instruction 2026-10-30). This overrides automatic major bumps, including for breaking changes; document compatibility impacts while retaining major 1. Preserve all other versioning rules, including minor/patch increments, synchronized metadata, commit/PR versioning and skipped Git tags. The version checker enforces this pin.
- Keep README's current source version and the newest numbered CHANGELOG.md entry synchronized. UI, health and FastAPI metadata derive their version from APP_VERSION.
- Run `python tools/check_version.py --base-ref <base-commit>` before publication; CI enforces this. Version metadata belongs in the tested commit.
- Every development and merge commit subject and PR title must include [vX.Y.Z]. Apply a matching GitHub version label where supported; inability to create a label must not block an otherwise valid update. Git tags are skipped by explicit user instruction.
- All applicable checks must pass on the exact final PR commit before merging. Record the version and PR/checkpoint references. Do not claim source versioning publishes a Docker image.

## Coordination between agents

Multiple agents may work on Mr Patchy concurrently. Use this repository's GitHub issues and PRs as the durable coordination record; agents may use different tools, sessions or the same GitHub account.

- At the start of each run, refresh current main, open issues, issue comments, open PRs and relevant PR reviews/checks. Reconcile unfinished work and ownership before selecting a task. Do not assume another agent's work is abandoned because a scheduled cycle ended.
- Before implementation, claim an existing issue in a comment, or create a scoped issue for an explicitly requested task that has none. Include an agent/session identifier, UTC timestamp, intended outcome, affected areas, branch/PR and next checkpoint. Assignees/labels supplement this record; the shared account name alone does not identify an agent.
- Re-read the issue and related PRs immediately after claiming and before substantial edits. A claim comment is not an atomic lock. If claims overlap, acknowledge the overlap on the issue and agree a division or handoff before proceeding. Work on independent unclaimed scope while waiting; do not duplicate an active fix.
- Use a separate focused branch and isolated checkout for each workstream. Open a linked draft PR as soon as there is reviewable work, record scope/dependencies on the issue, and update the same PR on later runs. Never reset another agent's checkout, push to its branch, overwrite its changes or take over its PR without an explicit handoff.
- Post concise GitHub checkpoints when scope changes, work blocks, a run ends or a handoff is needed: completed work, commit/PR, validation, remaining work and ownership. Release a claim explicitly when stopping; reclaim apparently stale work only after checking recent commits/comments and announcing the proposed takeover on the issue.
- Agents may review each other's PRs and respond to review comments. Record actionable findings and validation against the exact commit reviewed; identify the reviewing agent/session when accounts are shared, and never present self-review as independent approval. Coordinate dependencies, shared-file changes and merge order in linked issues/PRs.
- Serialize final integration and version allocation through the PRs. Inspect current main and pending versioned PRs before choosing a version; document the proposed version and merge order, without treating a comment as a lock. Immediately before merge, refresh main, resolve conflicts without discarding others' work, ensure the version is newer than main, synchronize metadata and rerun applicable checks on the exact final commit. If main advances or the final commit changes, reassess and rerun affected checks. Keep major 1 and all existing version/check requirements.
- Parallel work is allowed for independent tasks. A claimed task or blocked dependency is a coordination checkpoint, not a reason to create overlapping work or declare the roadmap complete. If all remaining actionable work is actively owned, report that state without speculative changes or a no-op version bump. If GitHub cannot be read or updated, report the access blocker instead of assuming ownership.
- Issue/PR discussion coordinates development; it does not grant runtime response authorization or change roles, audit, deployment or security boundaries. Close issues only after their full acceptance criteria are delivered and the tested merge is verified.
