# dhcpd case labels with hex constants (#1719)

Roadmap F slice (#1593), defect fix. The `case`/`default` label skip in
`app/dhcpd_execute.py` stopped at the first punctuation `:`. Inside a
parenthesized or argument case expression, the `:` of a colon-separated hex
constant (`parse_cshl`) ended the label early. The statements under the label
were then skipped, and the result still said `complete: True` with no gap.

What changed:

- The label now ends only at a punctuation `:` at parenthesis depth 0.
  `case concat("a", 1:2):` and `case (1:2:3):` report both programs, are
  complete and have no gap.
- If the depth-0 `:` follows a bare number or a hex-like name (`case 1:2:3:`,
  `case 1:`, `case beef:`), it is ambiguous. In a data switch, `parse_cshl`
  consumes that `:`. In a numeric switch, it ends the label. The switch
  expression's type is not modelled, so the result records a blocking
  `case_label_hex_colon` gap and `complete: False`. Parsing continues after
  that `:`, so programs are over-reported rather than dropped.
  `switch data or numeric context` is listed in `not_modelled`.
- If a label reaches `;`, `{`, `}` or the end of the file before a depth-0 `:`,
  the file is rejected with `colon_expected` (`parse_case_statement`'s
  "colon expected."). The skip no longer runs on into a later statement's `:`.

Validation: three regression tests in `tests/test_dhcpd_execute.py` failed on
main `60ca296` (v1.139.0) and pass with the fix. All 51 `tests/test_dhcpd_*.py`
tests pass. A trial with #1713's head `34b82e1` passed 121 dhcpd tests.

Remaining: the unparenthesized-label behaviour comes from reading the
4.4.3-P1 source. A native `dhcpd -t` differential was not available in this
environment. A numeric `switch (extract-int (...)) { case 1: ... }` now
reports a blocking gap even though dhcpd accepts it, a conservative cost until
switch typing is modelled.
