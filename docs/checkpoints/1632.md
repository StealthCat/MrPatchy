# Checkpoint: keyutils request-key callout contract (#1632)

Roadmap F (startup and scheduled-task awareness). Issue
[#1632](https://github.com/StealthCat/MrPatchy/issues/1632).

## 2026-11-27 — increment 1: pure contract

**Delivered** (branch `claude/vibrant-tesla-5sd08w`): `app/request_key_callouts.py`, a pure contract.
It takes captured `/etc/request-key.conf` text and the `/etc/request-key.d` listing (names in
`readdir()` order, entry kinds and text). It reports:

- the files `/sbin/request-key` reads, in order, and the drop-ins it skips;
- each rule's OP/TYPE/DESCRIPTION/CALLOUT patterns, whether the kernel's `create` upcall reaches it,
  the program, `|` pipe mode, argv (`argv[0]` is the basename) and macros;
- which inputs the requester controls: `%d`, `%c`, `%{type:description}` payloads and piped callout
  information. `runs_as` is `root`;
- lines that abort lookups, with the fields a request must match first, and whether the abort hits
  every kernel lookup;
- per-rule failures that only show when the rule is selected.

`select_rule()` replays request-key's best-match choice for one request.

The key native finding: a request made by uid 65534 (`keyctl request2 user 'mpk:x;y' 'cal lout'`)
made the kernel run the matching program as **uid 0, gid 0**. The program's argv carried the
description and callout information that the requester chose.

Parser rules match keyutils 1.6.3 `request-key.c`, checked natively:

- Drop-ins are read before `request-key.conf`, and every file is scanned before anything runs.
- Dot names, names not ending in `.conf`, and non-regular entries are skipped. On ext4 that includes
  symlinks.
- A line of 4096 bytes or more, counting its newline, aborts every lookup.
- A one-byte line is ignored, and so is a line starting with `#` or with white space.
- The last byte of every other line is dropped. Usually that is the newline. On a final line without
  a newline it is a real character: `/bin/last` ran as `/bin/las`.
- A short line aborts only lookups that match the fields read before it ends. Trailing white space
  counts as one more field read: `create user` aborted a `logon` lookup, but `create user ` did not.
- Best match is the smallest wildcard skip, compared left to right. A tie goes to the first line
  read.
- For `abc*def`, upstream compares the end of the datum with the *start* of the pattern: `c*e`
  matched `cxc` but not `cxe`.
- A program without `/` crashes (SIGSEGV). `%`, unknown one-letter macros and malformed `%{…}` fail.
  `%xy` stays literal and `%%` escapes.

Unchecked files or listings, unknown entry kinds, uncaptured text, NUL bytes, invalid UTF-8 and
over-limit input are blocking gaps. `origin` is `not_assessed` and `authorizes_response` is always
false.

**Validation** (Ubuntu 24.04, `keyutils 1.6.3-3build1`, kernel 6.18):

- 10 tests in `tests/test_request_key_callouts.py` encode native results:
  - real kernel upcalls with a recorder (uid/gid/argv, pipe stdin, a skipped symlinked drop-in);
  - `request-key -d -l -v` runs.
- Seeded differential of `select_rule()` against `request-key -d -l -v`. Configurations used random
  drop-ins (dot, non-`.conf`, symlinked), short and overlong lines, comments, leading white space,
  CRLF, missing final newlines, pipes, programs without a slash and all macros:
  - seed 20261127: 400 configurations, 2,400 requests;
  - seed 7: 400 configurations, 2,400 requests;
  - seed 11: 400 configurations, 2,400 requests.

  All 7,200 requests agreed on outcome, selected file:line, program, pipe mode and argv. The outcomes
  across them were 485 runs, 837 aborts, 249 failures and 5,629 no-matches. Seed 20261127 used the
  first generator profile. Seeds 7 and 11 used profiles with fewer short lines, and seed 11 also used
  more `*` patterns.
- Targeted mutations each fail the tests:
  - end-match quirk;
  - leading-white-space comment rule;
  - tie-breaking;
  - the root account.
- `ruff check` is clean. `check_version --allow-unversioned` passes.

**Not covered:** `%{type:description}` keysub was left out of the differential. Native debug mode
looks the key up for real. The contract reports the macro as requester-controlled and selection as
`runs`.

**Compatibility:** new files only. No schema, route, UI, auth, scheduling, agent or
response-authorization change.

**Next increments:** collector capture of the two paths (with entry kinds and `readdir()` order), then
Startup Files UI wiring.

## 2026-11-27 — increment 2: collector capture

**Delivered** (branch `claude/vibrant-tesla-jft6km`): agents hash `/etc/request-key.conf` (built-in
file) and the `/etc/request-key.d` drop-in directory (built-in root) as startup scope. Nothing is
parsed or run; the files are metadata and SHA-256 only, like the other built-in startup files.

- `app/persistence.py`: both paths are additive built-in scope, so an earlier complete inventory
  still compares within its own scope and lists them as newly covered.
- This is the first promoted *directory*. An administrator could previously store
  `/etc/request-key.d`, or a file inside it, as a custom path. Such a stored path is now covered by
  built-in scope (`target/agent.py` `PROMOTED_PERSISTENCE_ROOTS`, `promoted_custom_path()`), so
  saved monitor policies stay valid and the files are inventoried once. Only canonical paths are
  promoted; `..`, `//`, trailing `/` and control characters still fail validation.
- An earlier baseline that held such a custom path still compares: `compare()` accepts scope entries
  that disappeared only because a newly added built-in directory covers them, and keeps comparing the
  files under them (`previously_custom`). The startup view keeps those rows compared instead of
  marking them `not_in_baseline`. Any other narrowed scope still fails closed.
- `app/startup_inventory.py` labels both paths and states the parsing gap;
  `app/startup_catalog.py` adds the `request_key` event mechanism for both platform families.

**Validation:** `tests/test_request_key_scope.py` (30 cases) fails 18 of them on main `d316c8f` and passes
with the change. The other built-in scope suites (kdump, gitconfig, rsnapshot, TCP wrappers,
anacrontab) and the 54 persistence/startup test files (1,370 tests) pass. CI ruff selections and
`check_version --allow-unversioned` pass.

**Next increment:** agent-side rule parsing of the hashed bytes through
`app/request_key_callouts.py` and the Startup Files display.

## 2026-11-27 — increment 3: agent-side rule parsing and Startup Files display

**Delivered** (branch `claude/magical-goodall-fpuaer`):

- `target/agent.parse_request_key()` parses each file `/sbin/request-key` reads — `/etc/request-key.conf` and
  direct `/etc/request-key.d` children named `*.conf`, not starting with a dot, that are regular files — from
  the bytes the inventory already hashed. It mirrors `app/request_key_callouts` per file: rule patterns,
  pipe mode, `kernel_upcall`, requester-controlled inputs, `fails_when_selected`, `code_runs`, lines that abort
  lookups (with their scope and whether they hit every kernel lookup) and the dropped last byte of an
  unterminated final line. Commands use the cron best-effort redaction and are bounded to 512 characters,
  patterns to 256, rules and aborts to 64 per file. The first universal abort line is always kept, even past the
  abort limit. Text over 64 KiB, not UTF-8 or containing NUL yields `parsed: false` only. Nothing is executed and
  no new path is read.
- `app/persistence.validate_request_key()` strictly validates the report (exact keys, types, bounds, unique line
  numbers, `code_runs` consistency, pipe ⇔ `stdin_callout_info`, universal-abort-line consistency) and rejects it
  on paths request-key does not read or on non-regular entries. Parsed detail stays out of baseline comparison.
- `app/startup_inventory` marks each request-key entry `parsed`, `not_reported` (older agent), `skipped_name`,
  `skipped_kind`, `skipped_subdirectory` or `not_followed` (symlinked `request-key.conf`, which `fopen()` follows),
  attaches a cross-file `lookups` summary (universal aborts in any read file abort every lookup; `complete` is
  false when a read file was not parsed), adds rule counts to the Coverage catalog and makes commands and
  patterns searchable. The gap text is updated.
- Startup Files shows each rule's line, operation, key type, description, callout, command, requester-controlled
  inputs and whether it runs, plus lookup-aborting lines and an every-lookup-aborts notice.

**Validation:**

- `tests/test_request_key_rules.py` (80 tests): the agent agrees with `request_key_callouts.evaluate()` on 29
  fixtures and a seeded random differential of 1,500 configurations (seed 20261127) on rules, aborts and
  dropped last byte; redaction/escaping/bounds; limits; unreadable text; name rules; a real inventory over a
  temporary tree with skipped dot, `.bak`, subdirectory and symlinked drop-ins, where a `touch` marker command
  never runs; 36 controller rejection mutations; API view, catalog and search.
- `tests/ui_startup_request_key.cjs`: escaped rendering (an injected `<img onerror>` stays text), pipe and
  redaction notes, never/fails/aborted states, skipped/older-agent/unparsed files, no horizontal scroll at 320,
  768 and 1440 px, Coverage label. Run with the kdump and TCP wrappers modules in a focused runner.
- 1,145 startup/persistence/agent/inventory tests passed locally on SQLite.

**Not covered:** the `readdir()` order of drop-ins is not captured, so ties between equally specific rules in
different files are not resolved in the view. Package provenance and AI classification remain open.

**Compatibility:** additive optional `request_key` field on inventory rows from newer agents; older agents'
files show `not_reported`. No schema, route, auth, scheduling or response-authorization change.
